# The browser

A real Chromium view inside Emma, one session per thread. It keeps its own
cookies and its place, the agent drives the same session the user is looking at,
and it can sit either in the docked column or in a floating PIP window.

## Two places, one browser

`BrowserPane` draws the chrome — the tab strip, back, forward, reload, the
address bar, the clipboard drawer — and nothing else. The page itself is a
native `WebContentsView` owned by the main process, positioned by absolute
window coordinates that the pane pumps over `browserPlace`.

`browserPip(threadId, onClose)` wraps the same pane as a `PipWindow`, so the
floating window and the docked column are the same component and the same
session. Only one of them may be mounted for a thread at a time: two panes
pumping bounds for one session would fight over where the page goes.

Widen and hide are optional props. The PIP passes neither, so those two buttons
are absent there — the PIP's own header already folds it into the rail. The
window controls also carry a float/dock toggle whenever the caller hands the
pane an `onFloat`, which is how one form is swapped for the other.

## Where the page is allowed to paint

A native view paints above every pixel of DOM, so it has to be told to
disappear whenever something should be in front of it. The pane sends
`bounds: null` — which hides the view without touching the page — when:

- a modal `dialog` is open;
- the stage has collapsed to nothing;
- the pane is inside a PIP that is being dragged (`data-held`);
- the pane is inside a PIP that is stacked behind another (`data-depth` is not
  `0`), because the card in front is DOM and would otherwise be painted over.

A PIP folded into the icon rail is unmounted by `PipLayer`, and unmounting sends
`bounds: null` on the way out. The session, its tabs, and its cookies survive.

Bounds are read on every animation frame and only sent when they change. A
moving PIP resizes nothing, so a `ResizeObserver` never fires for it, and the
settle animation is a CSS transition with no event to listen to — reading the
rect each frame is the only thing that tracks both. An idle pane sends no IPC.

## Clipboard history

Up to 20 text items, in memory, for the run of the app. An item is recorded
when macOS `Command-C`, `Command-X` or `Command-V`, or Windows `Ctrl-C`,
`Ctrl-X` or `Ctrl-V`, is released inside a page in Emma's browser: the copy is
read 150 ms later, trimmed, capped at 4 KiB, and dropped if it repeats the item
already on top.

On macOS, anything the pasteboard marks `org.nspasteboard.ConcealedType`,
`TransientType` or `AutoGeneratedType` is skipped — that is how password
managers say "do not keep this", and Emma honours it. Windows uses the system
clipboard and has no equivalent pasteboard marker contract.

Picking an item from the drawer writes it back to the system clipboard, moves it
to the top of the ring, and pastes it into the page's focused field.

The hook is on key events, so a copy made from the page's context menu is not
recorded. The drawer is a drawer rather than a popover for the reason above: a
menu floating over the stage would be behind the page.

## The activity cursor

While a `browser` tool call is in flight, the input the agent sends to the page
is echoed as the same cue the computer tool draws over a native app: a grey
arrow haloed in the secondary accent that glides to the point, a pulse on
arrival, and a label naming what Emma is doing there. It is the tab's own input events that place it, so a
click, a hover, a fill or a drag marks the spot it landed on, and a snapshot, a
`get` or a scroll — none of which move a pointer — show nothing rather than
guess.

The overlay is a transparent, click-through window ordered directly above
Emma's own window, so it cannot take focus, cannot swallow a click the user
means for the page, and never moves the real pointer. It is dropped when the
pane is hidden or the window is not on screen, expires 1.4 seconds after the
last point, and the window itself is closed after a minute with no browser
work. The coordinates stay inside Emma: they are not added to the tool result
the model reads.

[`main/browser.ts`](../desktop/main/browser.ts) turns a tab's input events into
that cue, `reportBrowserCursor` in [`main/main.ts`](../desktop/main/main.ts)
places the window, and `ComputerActivityCursor` in
[`src/App.tsx`](../desktop/src/App.tsx) paints it — the same component, window
and stylesheet as [computer use](computer-use.md#activity-cursor).

## The agent

The `browser` tool drives the session by thread id over CDP, through
`agent-browser` pinned to the tab's target. None of that depends on where the
pane is drawn, or on whether it is drawn at all — a PIP browser answers
`snapshot`, `get`, `click` and `fill` exactly as the docked one does. What the
agent does is visible to the user in the same window, and what the user does is
there for the agent to read.
